## 1. 项目概述

**一句话定位**：把我司的招聘撮合业务从三方平台搬回自己地盘，让简历资产从第一天开始沉淀。

**业务三问（CEO口述存档）**：

- **给谁用**：
  - B端：BOSS/企业管理员/HR/招聘专员——注册登录招聘端，企业认证后发布JD，查看投递来的简历，与牛人留言沟通，约面直至发offer
  - C端：牛人/求职者——注册后选择求职方向，编写并发布在线简历，搜索匹配职位，与BOSS沟通约面
  - 平台（我司）：系统管理员 + 企业运营官 + 简历优化师/牛人运营官 + 私域运营官
- **解决什么问题**：现状是我司招聘撮合业务全程发生在三方平台——职位在三方发、简历从三方下载、B-C沟通看不见，导致简历资产无法沉淀、撮合过程不受掌控、服务模式无从积累。本期把招聘流程搬回自己地盘，简历和撮合关系从第一天沉淀在我司。
- **什么算成功**：见第9节成功标准（四把尺+时间框）。

**版本分层（终局倒推法）**：

- v1.0（本期）：双边流程线上化，简历开始沉淀
- v1.x（近期）：简历池规模化后增强运营工具（看板增强、运营系统支撑）
- v2.0（终局，仅记录不实现）：简历数据清洗分析 → 人岗高度匹配 → 卖服务

**冷启动策略**：B端种子 = 我司自入驻 + 存量企业客户搬入；C端种子 = 三方平台存量简历人群私域引导注册。

## 2. 用户与角色

| 端 | 角色 | 本期系统支撑 |
|---|---|---|
| C端·牛人H5 | 求职者（牛人） | 全部核心功能 |
| B端·HR H5 | 企业管理员/HR | 全部核心功能 |
| Admin·管理后台 | 系统管理员 | 最高系统权限（配置类）；**敏感数据脱敏可见——只管系统，不管运营明细** |
| Admin·管理后台 | 企业运营官/简历优化师/牛人运营官/私域运营官 | **愿景层编制**：本期系统仅支撑其工具底座（企业审核/用户管理/数据看板），人工服务职能不做系统化 |

**权限设计要点**：接口按角色鉴权；系统权限与数据可见性分离（管理员可管理系统配置，但简历正文等敏感运营数据脱敏/不可见）。

## 3. 核心业务流程

```
【企业线】HR注册 → 提交企业认证 → 平台审核 ──驳回→ 修改重提
                                          └─通过→ 发布职位 →（职位审核）→ 上架
【牛人线】注册 → 选求职方向 → 编写在线简历 → 搜索/筛选职位 → 查看JD → 一键投递
【撮合线】投递产生 → HR收投递 → 查简历 + 留言沟通 → 状态流转 → 约面/发offer/婉拒
```

- **留言模型**：一次投递 = 一个会话。投递是沟通的门票：先投递，再开聊。
- **投递状态机**：`待查看 → 已查看 → 约面 → 已发offer / 不合适`（单向流转，HR操作）。
- **意向筛选排序**（字段级匹配，非算法推荐）：牛人职位列表按其求职意向（期望岗位方向/期望城市/期望薪资）优先排序；HR投递列表带"意向匹配"标记、匹配优先。

## 6. 技术架构

```
C端·牛人H5（Vue3，竖屏）─┐                          ┌─ dev_db  （本机MySQL，开发测试）
B端·HR H5（Vue3，竖屏）─┼→ Java后端（REST API，     ─┤
Admin·后台（Vue3，桌面）─┘   按角色鉴权，JWT）        └─ prod_db （生产库，双库隔离）

三个前端站编译产物为纯静态文件 → EdgeOne Pages 部署（现有管道复用×3，0成本）
后端生产部署方案：第1关技术选型决策会拍板（硬指标见第8节）
```

**分层原则**：前端只管显示，后端只管业务规则与数据，数据库双库隔离——dev环境任意折腾不伤生产。

## 7. 数据模型概要（7张表，第2关ER评审细抠）

```
users ──1:N── resumes ──1:N── resume_experiences   （牛人线）
companies ──1:N── jobs                             （企业线）
jobs ──N:M── users（通过 applications）             （撮合线）
applications ──1:N── messages                      （一次投递=一个会话）
```

**为终局攒数据的钩子**（v2.0数据服务的地基，本期只存不析）：

- `resumes` 含期望岗位方向/期望城市/期望薪资——意向匹配与将来分析的原料
- `applications` 含状态机各环节时间戳——将来分析"投递到offer转化周期"
- `users.password` 只存加密哈希，永不存明文

## 8. 非功能需求

| 类别 | 要求 |
|---|---|
| 成本红线 | 全链路0元：前端EdgeOne免费、后端免费层（第1关选型）、MySQL本机免费 |
| 密钥安全 | 配置与代码分离（.env + .gitignore）；上线前 `git ls-files` 安检；密钥永不进代码/仓库/聊天 |
| 账号安全 | 密码bcrypt加密存储；接口按角色鉴权（防越权：牛人进不了HR功能，HR进不了Admin） |
| 可用性 | 免费层有冷启动休眠（约15分钟无访问即休眠，Java唤醒慢）。**对策：keep-alive保活**——定时器每10分钟访问后端 `/api/health`；方案A（GitHub Actions cron，公开仓库免费）或方案B（UptimeRobot免费监控+宕机邮件告警），第1关选型时定。**保活可行性=选型一票否决项**（额度需容纳单实例7×24，参考：Render免费层750h/月>744h/月） |
| 合规 | 收集手机号/简历=个人信息（Day 5合规课存档）；本期为仿真项目不上真人数据；真上线触发备案倒推（按运维手册"〇、域名决策记录"） |
