## 3. 数据库设计（ER图 + 数据字典）

### 3.1 ER关系图

```
users(1)─────(1)resumes(1)─────(N)resume_experiences   牛人线：一人一份简历，简历挂多条经历
users(1)─────(1)companies                              企业线：一个HR建一家企业
companies(1)─────(N)jobs                               企业发多职位
jobs(N)──────(M)users   经由 applications              撮合线：多对多
applications(1)─────(N)messages                        会话线：一次投递一个会话
dict_items（独立）                                     字典线：运营词汇统一管理
  ↑ 软引用（应用层校验，不建外键）：
  jobs.category / resumes.expect_category  ← dict_type=category
  companies.industry / jobs.city / resumes.expect_city / 学历 ← 对应字典类型
```

### 3.3 字典表 dict_items（v1.1新增，CEO评审意见：运营词汇入库）

**dict_items 通用字典表**（一张表管所有字典类型）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGINT | PK, AUTO | |
| dict_type | VARCHAR(30) | NOT NULL | 字典类型：category岗位方向 / industry行业 / city城市 / education学历 |
| code | VARCHAR(50) | NOT NULL | 存储值（业务表引用它，稳定不改） |
| label | VARCHAR(50) | NOT NULL | 显示名（运营可随时改，不影响存量数据） |
| sort | INT | DEFAULT 0 | 排序 |
| status | TINYINT | DEFAULT 1 | 1启用 / 0停用（停用=新内容不可选，存量数据不受影响） |
| created_at / updated_at | DATETIME | | |
| 约束 | **UNIQUE(dict_type, code)** | | 同类型内值唯一 |

**初始化字典数据（种子）**：

| dict_type | 初始值 |
|---|---|
| category | 后端开发/前端开发/移动开发/测试/产品经理/运营/设计/其他 |
| industry | 互联网/金融/教育/制造/医疗/零售/其他 |
| city | 北京/上海/深圳/广州/杭州/成都/武汉/西安（=平台开通城市，运营可扩） |
| education | 学历不限/大专/本科/硕士/博士 |

**字典设计三原则**：
1. **运营词汇进字典，系统词汇进代码**——状态机（投递状态/审核状态）、角色永不入字典（判据：管理员改了它，系统会不会坏）
2. **code与label分离**——业务表存code，页面显示label；运营改显示名零成本
3. **软引用**——业务表到字典不建外键（应用层校验），换取运营调整的灵活性

> jobs.category 与 resumes.expect_category 共用 category 字典仍是**意向匹配的根基**：两边code同源，匹配才是 apples-to-apples。

## 4. REST接口文档（按端分组）

**通用约定**：前缀`/api`；认证后带 `Authorization: Bearer <JWT>`；统一响应 `{code, msg, data}`；分页 `page, size`。

### 4.1 公共

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/auth/register | 注册（body带role：CANDIDATE/HR；ADMIN不开放注册，种子数据内置） |
| POST | /api/auth/login | 登录→返回JWT |
| GET | /api/health | 健康检查（**keep-alive的靶子**，免鉴权） |
| GET | /api/dicts?type=category/industry/city/education | 字典读取（免鉴权，三端下拉框数据源） |

### 4.2 C端·牛人（JWT role=CANDIDATE）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /api/jobs?category=&city=&kw=&page= | 职位列表：**有简历时按意向匹配排序**（category>city>薪资，CASE打分ORDER BY） |
| GET | /api/jobs/{id} | 职位详情（含企业信息；未上架404） |
| POST | /api/applications | 投递（校验：简历已发布；UNIQUE挡重复投） |
| GET | /api/my/applications | 我的投递列表（含状态） |
| GET | /api/applications/{id}/messages | 拉取会话留言 |
| POST | /api/applications/{id}/messages | 发送留言 |
| GET / PUT | /api/my/resume | 读/改简历主表 |
| POST / PUT / DELETE | /api/my/resume/experiences | 项目经历增改删 |

### 4.3 B端·HR（JWT role=HR）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /api/companies | 提交企业认证（status=PENDING） |
| GET | /api/my/company | 我的企业（含审核状态） |
| POST | /api/jobs | 发布职位（校验：企业APPROVED；发布后PENDING待审） |
| GET | /api/my/jobs | 我的职位列表 |
| PUT | /api/jobs/{id}/status | 上架/下架（ACTIVE/OFF，仅自己的职位） |
| GET | /api/my/jobs/{id}/applications | 该职位投递列表（**意向匹配标记+排序**：牛人期望vs职位要求打标） |
| PUT | /api/applications/{id}/status | 状态流转（VIEWED/INTERVIEW/OFFER/REJECTED，写对应时间戳） |
| GET / POST | /api/applications/{id}/messages | 与C端共用会话接口（权限校验：会话双方） |

### 4.4 Admin（JWT role=ADMIN）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /api/admin/companies?status= | 企业列表 |
| PUT | /api/admin/companies/{id}/audit | 企业审核（APPROVED/REJECTED+理由） |
| GET | /api/admin/jobs?status= | 职位列表 |
| PUT | /api/admin/jobs/{id}/audit | 职位审核 |
| GET | /api/admin/users?role=&kw= | 用户列表（**手机号脱敏显示**：138****5678——PRD权限设计落地） |
| PUT | /api/admin/users/{id}/status | 禁用/启用 |
| GET | /api/admin/stats | 看板：企业数/职位数/投递量/简历数 |
| GET / POST / PUT / DELETE | /api/admin/dicts | **字典管理（v1.1新增）**：4类字典增删改、排序、启停 |

## 5. 页面流转

```
【C端·牛人H5】（底部Tab：职位 | 我的投递 | 我的）
 未登录→登录/注册 → 职位列表(意向优先) → 职位详情 →投递(无简历先引导去建)
 我的投递 → 卡片(状态) → 会话页(留言，10秒轻轮询+下拉刷新)
 我的 → 我的简历(编辑：主表+经历多条)

【B端·HR H5】
 注册→企业认证(提交资质) →[APPROVED]→ 发布职位
 职位管理(上架/下架) → 投递列表(意向标记) → 处理(状态流转) → 会话页

【Admin·桌面】（左侧菜单）
 登录 → 数据看板(首页)
 企业审核 | 职位审核 | 用户管理
```

## 6. 关键技术决策

| 决策 | 方案 | 理由 |
|---|---|---|
| 会话认证 | JWT（无状态） | 免费层多实例无session共享问题；secret走环境变量 |
| 密码 | bcrypt | 行业标准，PRD非功能要求 |
| 意向匹配 | SQL层 `ORDER BY CASE`打分（category=3分>city=2分>薪资区间1分） | PRD钉死的"字段级筛选排序"，一行SQL，不引算法 |
| 字典机制（v1.1） | 通用字典表dict_items+软引用（不建外键） | 运营词汇入库可配置（CEO评审意见）；状态机/角色永不入字典 |
| 简历照片（v1.1） | 前端压缩→Base64入TEXT（≤200KB）；列表查询不带photo | 无对象存储（COS备案墙）下的降级保真；真实形态=对象存储+URL，触发日迁移 |
| 留言刷新 | 会话页10秒轻轮询+手动下拉刷新 | 留言板模式（PRD裁决），不上WebSocket |
| CORS | 后端白名单三站域名 | 前后端分离标配 |
| 双库切换 | Spring Profiles（dev/prod yml） | 数据库分离落地；prod连接串走环境变量不进库 |
| 内存红线 | JVM `-Xmx320m -Xss512k`；依赖精简（web/validation/mybatis/jwt/bcrypt，不装全家桶） | 512MB免费层（ADR-001风险节） |
| ORM | MyBatis（预编译） | 防SQL注入+SQL可控（意向匹配的CASE打分要手写SQL） |

## 7. 安全设计

1. **密钥**：数据库密码/JWT secret 全走 `.env`（本地）与环境变量（Render）；`.env` 在 `.gitignore`；上线前 `git ls-files` 安检
2. **越权防护**：角色拦截器（路径级）+ 资源属主校验（HR只能操作自己职位的投递；会话只有双方可读写）
3. **注入防护**：MyBatis 全预编译 `#{}`，禁 `${}`
4. **管理员脱敏**：手机号中间四位掩码（PRD"只管系统不管运营明细"落地）
5. **投递门槛**：简历未发布不可投；同一职位 UNIQUE 挡重复
